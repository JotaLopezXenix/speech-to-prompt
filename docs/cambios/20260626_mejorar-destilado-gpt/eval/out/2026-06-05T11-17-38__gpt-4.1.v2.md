Objetivo y contexto

Quiero rediseñar el flujo de procesado y visualización de valoraciones de fotos en nuestra aplicación, asegurando que el objeto central sea la foto, no las ejecuciones. Actualmente, la base de datos parte vacía, con tres tablas: ejecuciones, fotos y scores. Al iniciar, tenemos 18 archivos ARW y solo 4 tienen ficheros XMP producidos manualmente por Manuel (Lightroom). Al lanzar el ranking, la aplicación inserta filas en scores aunque la valoración no cambie, lo que genera duplicidades innecesarias y ruido en el histórico.

Requisitos para el flujo de procesado

- Al procesar cada foto:
  - Comprobar si existe XMP y si su puntuación difiere de la última registrada.
  - Si hay cambio, guardar la nueva puntuación externa en scores.
  - A continuación, ejecutar el ranking automático con los parámetros actuales.
  - Solo si la nueva puntuación automática es distinta de la última, guardar la nueva valoración (y el XMP full content).
  - Si no ha variado nada (ni externa ni automática, ni parámetros), no insertar filas nuevas.

- Debo conservar todo el histórico de valoraciones relevantes: solo inserciones cuando hay cambios, nunca duplicados si no cambian las puntuaciones.
- La tabla scores debe almacenar para cada foto:
  - el ranking actual (último ID autonumérico)
  - el agente (manual o automático)
  - la fecha
  - el XMP full content y el hash.

- En la tabla ejecuciones, cada fila debe asociar los parámetros usados en esa ejecución, para facilitar la trazabilidad y el refinado.
- Los parámetros (umbral de score, modo de lectura RAW, ventana ráfaga, etc.) deben guardarse en una tabla aparte, que puede ser horizontal (una fila por ejecución, columnas para cada parámetro) o vertical (código, descripción, valor).

Visualización y UX

- En la pantalla principal, tras seleccionar la carpeta de sesión:
  - Mostrar la lista de fotos con:
    - nombre de archivo,
    - puntuación actual (estrellas, agente, fecha),
    - última puntuación externa (valor, agente, fecha),
    - diferencia entre puntuación automática y externa (columna de discrepancia),
    - filtro para solo discrepancias.
  - Cada fila debe ser pinchable, abriendo pantalla individual con miniatura, histórico completo de valoraciones y parámetros con los que se obtuvieron.
  - El botón "ejecutar ranking" debe ser realmente "procesar/reprocesar carpeta".
  - El botón "capturar cambios manuales" ya no es necesario; al reprocesar la carpeta se detectan cambios externos (Lightroom) automáticamente y se insertan si procede.
  - Los parámetros deben gestionarse en pantalla aparte conectada con la pantalla principal.

Consideraciones técnicas y dudas

- ¿Es preferible guardar los parámetros por ejecución de forma horizontal o vertical en la base de datos? ¿Algún patrón óptimo para la tabla de parámetros según Claude Code?
- Voy a guardar el XMP full content en cada score cuando haya cambio de rating, dado que no deberían crearse muchos registros.
- El umbral de fotos con rating externo que disparaba la confirmación ya no parece necesario, dado que guardaremos todo el histórico. Confirmar si Claude Code está de acuerdo.
- El flujo debe cubrir tanto sesiones iniciales (fotos solo valoradas a mano), mixtas, y posteriores reprocesos.
- La visualización debe facilitar la comparación rápida entre valoraciones externas y automáticas, permitiendo filtrar diferencias y ver el histórico completo de cada foto.

Resumen de estructura

- Centralidad de la foto: historial de valoraciones relevante, nunca duplicadas.
- Scores: solo insertamos cuando cambia la valoración (externa o automática); guardamos el XMP full content.
- Ejecuciones: guardan parámetros asociados.
- Parámetros: tabla aparte, pendiente decidir formato óptimo.
- UX: pantalla principal con lista pinchable, comparación clara entre valoraciones actuales y externas, pantalla de parámetros, filtrado de discrepancias, pantalla individual para cada foto.
